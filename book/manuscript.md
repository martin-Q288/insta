# AI 활용할 줄은 아는데 어떻게 수익화 할까

자는 동안 모객하고 응대하는 판매 자동화 만들기

---

## 이 자료가 만드는 것

만드는 건 이미 하실 줄 압니다. 문제는 **만든 다음**입니다.

상품을 올려두고 글을 몇 개 쓰면, 며칠 반응이 없고 그러다 지칩니다.
손으로 하면 반드시 그렇게 됩니다. 사람은 새벽 3시에 달린 댓글에 답할 수 없고,
매일 같은 밀도로 글을 쓸 수도 없기 때문입니다.

**이 자료는 그 일을 대신하는 시스템을 만듭니다.**

```
   [상품]  ──▶  [판매 채널]
                    │
                    ▼
   ┌──────────────────────────────────┐
   │  ①  자동 발행    정해진 순서로 글을 올린다 │
   │  ②  자동 응대    달린 댓글에 몇 분 안에 답한다 │
   │  ③  자동 중계    판매 상황을 사건으로 만들어 올린다 │
   └──────────────────────────────────┘
                    │
                    ▼
              [문의 · 구매]
```

세 부품이 24시간 돌아갑니다. 사람이 하는 일은 **판매 수량을 입력하는 것과
민감한 문의를 넘겨받는 것** 둘뿐입니다.

### 이 자료가 주는 것

- 스레드 공식 API 세팅 — 앱 생성부터 토큰 발급까지
- 발행 · 응대 · 중계 **세 봇의 시스템 프롬프트 전문**
- 답글에 답할지 넘길지 숨길지 **판단 기준 설계**
- 계정이 죽지 않게 하는 **안전장치** (한도·멱등성·금지 표현)
- 전환율을 올리는 배치 — 링크 위치, 상담 창구, 가격 정책
- **카테고리별 페인포인트 지도** — 그래서 무엇을 만들어 팔 것인가
- 결제 · 전달 · 법무 최소 세트

### 다루지 않는 것

- AI 도구 기초 사용법 (질문해 본 적 있으면 충분합니다)
- 브라우저 자동화 · 계정 다중 운영 같은 약관 위반 방식
- 유료 광고 집행
- 법률 · 세무 자문 (실무 정리까지)

### 필요한 것

- ChatGPT 또는 클로드 계정
- 인스타그램 계정 (스레드는 여기에 붙습니다)
- **코딩은 몰라도 됩니다.** 필요한 코드는 AI가 씁니다.
  다만 터미널에 명령어를 붙여넣고 결과를 확인할 수는 있어야 합니다

## 1. 왜 자동화인가 — 반응 속도가 전환율입니다

### 손으로 하면 지는 이유

같은 글을 올려도 결과가 갈리는 지점은 글의 품질이 아니라 **반응 속도**입니다.

댓글이 달렸을 때 5분 안에 답이 달리면 대화가 이어집니다. 반나절 뒤에 달리면
그 사람은 이미 떠났습니다. 그리고 플랫폼 알고리즘은 **댓글 수와 대화의 길이**를
봅니다. 답이 빠를수록 대화가 길어지고, 대화가 길어질수록 더 많이 노출됩니다.

**사람은 이걸 못 합니다.** 잠을 자야 하고, 본업이 있고, 무엇보다 반응이 없는
날에는 의욕이 꺾입니다. 자동화의 실제 가치는 발행량이 아니라 **꺼지지 않는
반응 속도**입니다.

### 판매 자체를 콘텐츠로 만들 수 있습니다

상품 소개는 한 번 하면 더 쓸 말이 없습니다. 그런데 **판매 진행을 중계하면
소재가 계속 생깁니다.**

오픈했습니다 → 여섯 시간째 0건입니다 → 첫 건이 나왔습니다 →
세 건째라 가격이 올랐습니다 → 절반입니다 → 마감했습니다.

**안 팔리는 것조차 소재가 됩니다.** "아직 0건"은 실패 보고가 아니라
다음 화 예고입니다. 이걸 사람이 매번 쓰기는 어렵지만, 판매 수량만 넣으면
자동으로 나가게 만들 수 있습니다.

### 그리고 파는 글보다 답하는 글이 퍼집니다

판매 목적의 글은 확산되지 않습니다. **판매와 무관한 질문에까지 성실히 답하는
계정**이 확산됩니다. 알고리즘이 대화를 보기 때문이기도 하고, 사람이 광고를
읽지 않기 때문이기도 합니다.

이 자료의 응대 봇이 **상담 모드**로 설계된 이유가 그것입니다.
상품 얘기를 먼저 꺼내지 않습니다.

## 2. 전체 구조 — 부품 여섯 개

| 부품 | 하는 일 | 사람이 개입하는가 |
|---|---|---|
| **설정 파일** | 상품 정보, 가격 정책, 한도, 금지 항목 | 처음 한 번 |
| **글 목록** | 판매 전에 깔아둘 글 (순서 지정) | 처음 한 번 |
| **발행 봇** | 정해진 일차에 글을 올린다 | 없음 |
| **응대 봇** | 달린 댓글을 읽고 답한다 | 민감 건만 넘겨받음 |
| **중계 봇** | 판매 사건이 생기면 글을 쓴다 | **판매 수량 입력** |
| **상태 파일** | 무엇을 올렸고 무엇에 답했는지 기록 | 없음 |

**상태 파일이 핵심입니다.** 이게 없으면 같은 글이 두 번 올라가고 같은 댓글에
두 번 답합니다. 그 순간 계정이 봇으로 보입니다.

### 왜 공식 API를 쓰는가

브라우저를 조작해 로그인 세션을 흉내 내는 방식이 돌아다니지만 **쓰지 마십시오.**
약관 위반이고 계정 정지 위험을 집니다.

공식 API의 한도는 **글 250건/일, 답글 1,000건/일**입니다.
실제 필요량의 수십 배입니다. 위험한 쪽을 갈 이유가 없습니다.

## 3. 세팅 ① — 스레드 앱과 토큰

여기가 가장 많이 막히는 지점입니다. 순서대로 하십시오.

### 준비물

1. **인스타그램 계정** — 스레드는 여기에 붙습니다
2. **스레드 계정** — 인스타에서 연결하면 생깁니다
3. **메타 개발자 계정** — 개발자 사이트에서 가입

### 순서

**① 메타 개발자 콘솔에서 앱을 만듭니다.**
앱 유형에서 **스레드용**을 선택합니다. 목록에 없으면 앱을 만든 뒤
제품 추가에서 Threads API 를 붙입니다.

**② 권한(스코프) 세 개를 켭니다.**

| 권한 | 왜 필요한가 |
|---|---|
| `threads_basic` | 모든 호출의 기본 |
| `threads_content_publish` | 글·답글 발행 |
| `threads_manage_replies` | 답글 숨기기 |

**셋 다 필요합니다.** 하나라도 빠지면 해당 기능에서 권한 오류가 납니다.

**③ 리디렉션 URI를 등록합니다.** 로컬에서 돌릴 거면 `https://localhost/`
같은 값으로도 됩니다. 다만 **등록한 값과 호출할 때 쓰는 값이 정확히 같아야
합니다.** 슬래시 하나 차이로 실패합니다.

**④ 단기 토큰을 받고 장기 토큰으로 교환합니다.**
단기 토큰은 한 시간 남짓이라 자동화에 못 씁니다. **반드시 장기 토큰으로
교환하십시오.** 장기 토큰은 유효기간이 있고 갱신이 필요합니다.

**⑤ 사용자 ID를 확인합니다.** 숫자 값이고, 발행 시 경로에 들어갑니다.

### 자주 나는 오류

| 증상 | 원인 |
|---|---|
| 권한 오류 | 스코프 누락. 셋 다 켜졌는지 확인 |
| 리디렉션 불일치 | 등록값과 호출값이 다름 (슬래시 유무 포함) |
| 하루 만에 토큰 만료 | 단기 토큰을 그대로 씀. 장기로 교환할 것 |
| 호스트 오류 | 문서마다 도메인 표기가 섞여 있음. 한쪽으로 통일해서 시험 |

**토큰은 절대 코드나 저장소에 그대로 두지 마십시오.**
환경변수로 넣고, 실수로 올라갔으면 즉시 폐기하고 다시 발급받으십시오.

## 4. 세팅 ② — 발행은 두 단계입니다

이 구조를 모르면 코드가 안 돌아갑니다.

```
1단계  컨테이너 생성   POST /{user-id}/threads
                      media_type=TEXT, text=본문
                      → creation_id 를 받는다

2단계  발행           POST /{user-id}/threads_publish
                      creation_id=위에서 받은 값
                      → media_id 를 받는다
```

**두 단계 사이에 잠깐 기다려야 합니다.** 컨테이너가 준비되기 전에 발행을
호출하면 실패합니다. 몇 초 정도 두는 것이 안전합니다.

### 답글도 같은 구조입니다

컨테이너를 만들 때 **`reply_to_id`** 에 상대 답글의 ID를 넣으면 그 답글에
달립니다. 나머지는 동일합니다.

### 조회에서 반드시 틀리는 지점

| 호출 | 무엇이 나오나 |
|---|---|
| `GET /{media-id}/replies` | **내 글에 달린 답글** ← 이게 필요한 것 |
| `GET /{user-id}/replies` | **내가 쓴 답글** ← 이걸 쓰면 안 됨 |

**두 번째를 쓰면 봇이 자기 답글에 답합니다.** 흔한 사고입니다.

그리고 응답에 **내가 쓴 답글인지 표시하는 값**이 함께 옵니다.
그것도 걸러내야 무한 루프가 안 생깁니다.

### 글자 수 제한

**500자**입니다. 그런데 **이모지는 글자 하나가 아니라 여러 바이트로 계산됩니다.**
한글은 1자로 셉니다. 이모지를 많이 쓰면 예상보다 일찍 걸리므로,
발행 전에 길이를 검사해서 초과하면 아예 올리지 않도록 막아야 합니다.

## 5. 무엇을 언제 올릴 것인가

세팅보다 이게 더 중요합니다. **순서를 틀리면 계정이 죽습니다.**

### 3일 구조

| 일차 | 글의 성격 | 판매 |
|---|---|---|
| 1일차 | 자기소개 · 문제 제기 · 내가 확인한 사실 | 없음 |
| 2일차 | 실무 정보 무료 공개 · **상담 창구 열기** | 없음 |
| 3일차 | 가격 정책 설명 · 오퍼 | 여기서만 |

**자기소개가 첫 글입니다.** 신규 계정이 결과물 자랑이나 판매로 시작하면
그 즉시 홍보 계정으로 분류되고 도달이 깎입니다.

**상담 창구가 판매보다 먼저입니다.** 이게 순서의 핵심입니다.
이틀 동안 답을 받아본 사람이 사흘째에 삽니다. 반대로 하면 아무것도 안 팔립니다.

### 첫 두세 개는 손으로 올리십시오

팔로워 0인 새 계정이 첫날부터 API로만 발행하는 건 굳이 만들 필요 없는
스팸 신호입니다. 계정이 살아 있는 걸 확인한 뒤에 자동화를 켭니다.

### 실적이 없다는 사실을 먼저 밝히십시오

숨기다 들키는 것보다 강합니다. 그리고 이걸 먼저 말하면 **나머지 주장의
신뢰도가 올라갑니다.** 불리한 것을 밝힌 사람이 하는 말이기 때문입니다.

다만 **없는 것과 있는 것을 섞지 마십시오.** AI로 판 실적은 없어도
다른 판매·운영 경험이 있다면 그건 근거입니다. 주어를 정확히 쓰면 됩니다.

## 6. 발행 봇 프롬프트

글을 미리 다 써두는 방식과, 상황을 주고 그때그때 쓰게 하는 방식이 있습니다.
**판매 전 글은 미리 써두고, 판매 시작 후에는 상황 기반으로 생성**하는 것이
안전합니다.

### 미리 쓰는 글의 형식

```
# id: 00-intro          ← 멱등성 키. 같은 id는 두 번 안 올라간다
# day: 1                ← 첫 발행일 기준 상대 일차
본문 (최대 500자)
===
# id: 01-...
```

**`id`가 상태 파일의 키가 됩니다.** 이게 없으면 재실행할 때마다 같은 글이
다시 올라갑니다.

**`day`가 판매 글이 1일차에 나가는 사고를 막습니다.** 코드가 이 값을 보고
순서를 강제하게 만드십시오. 사람이 기억으로 지키면 반드시 언젠가 틀립니다.

### 미기입 자리 차단

원고에 `[[여기에 링크]]` 같은 자리표시자를 남겨두는 실수가 흔합니다.
**평소 글에 안 쓰는 기호로 감싸두고, 그게 남아 있으면 발행을 중단**하도록
검사를 넣으십시오. 건너뛰면 안 됩니다 — 뒤 글이 먼저 올라가서 순서가 무너집니다.

> 이 검사는 실제로 작동합니다. 이 자료를 만들 때도 위 예시 문장이
> 검사에 걸려서 빌드가 멈췄습니다. 기호는 본문에서 절대 안 쓸 것으로
> 고르십시오.

## 7. 응대 봇 — 이 자료의 핵심

여기가 매출을 만듭니다. 발행은 도달을 만들고 **응대가 전환을 만듭니다.**

### 네 가지 판단

모든 답글을 답하면 안 됩니다. 네 갈래로 나눕니다.

| 판단 | 언제 |
|---|---|
| **reply** | 질문·의견·감사. 답할 내용이 있는 경우 |
| **skip** | 스팸, 의미 없는 반응, 이미 끝난 대화 |
| **hide** | 욕설, 혐오 표현, 무관한 홍보 링크 |
| **escalate** | 사람이 봐야 하는 것 — 답글을 쓰지 않고 넘긴다 |

**escalate 목록을 반드시 채우십시오.** 공개 답글이 잘못 나가는 비용이
늦게 답하는 비용보다 훨씬 큽니다.

기본으로 넣을 항목입니다.

- 환불 · 결제 분쟁
- 법적 조치 언급이나 신고 예고
- 개인정보 · 계정 접근 요구
- 수익 보장을 요구하거나 수익 인증을 요구하는 것
- 구체적인 세무 · 법률 판단 요구
- 심한 비방이나 명예훼손 소지가 있는 주장

### 상담 모드로 설계합니다

**판매 안내 봇이 아니라 상담 창구여야 합니다.**
판매와 무관한 질문에도 답하고, **상품은 상대가 직접 물었을 때만** 꺼냅니다.

"자세한 건 전자책에 있습니다" 같은 유도도 하지 마십시오.
답변에 판매 의도가 비치는 순간 그 답변의 값어치가 떨어집니다.

### 시스템 프롬프트 — 그대로 쓰셔도 됩니다

```
너는 스레드 계정 [계정명]의 답글을 쓴다.

<너는 누구인가>
너는 사람이 아니라 AI다. 이름은 [이름].
이 계정의 글은 네가 쓴다.
- 사람인 척하지 않는다. AI냐고 물으면 그렇다고 답한다.
- 네 실적은 이 프로젝트에서 실제로 팔린 수량뿐이다.
- 감정이나 경험을 지어내지 않는다. "저도 예전에 그랬어요" 금지.

<운영자의 경력 — 네 것이 아니다>
아래는 운영자의 경력이다. 절대 1인칭으로 말하지 마라.
"제가 ~했고"가 아니라 "운영자는 ~했고"로 쓴다.
[경력 나열]

<이 계정은 상담 창구다>
네 일은 파는 게 아니라 답하는 것이다.
판매와 무관한 질문이 와도 성실히 답한다.
팔려고 쓴 글은 안 퍼지고 도와주려고 쓴 글은 퍼진다.

<참고로 알고 있을 것 — 먼저 꺼내지 않는다>
이름: [상품명]
설명: [한 줄]
다루는 내용: [항목 나열]
가격: [정책]
구매자가 따로 준비해야 하는 것: [항목]
문의 방법: [경로]

<상품 얘기를 꺼내도 되는 때>
상대가 다음을 직접 물었을 때만이다.
- 가격이 얼마인지
- 어디서 사는지
- 무슨 내용이 들어 있는지
- 이 상품이 자기 상황에 맞는지
그 외에는 언급하지 않는다. "자세한 건 ~에" 같은 유도도 하지 않는다.

<절대 하지 않는 것>
- 수익·성과를 보장하거나 추정하지 않는다.
- 위 <참고>에 없는 기능·가격·조건을 만들어내지 않는다.
- 법·세무 사항을 단정하지 않는다. 실무 정리라는 걸 밝히고,
  확인이 필요하면 그렇게 말한다.
- 특정 플랫폼 정책을 확인 없이 단정하지 않는다. 정책은 바뀐다.
- 개인정보를 답글로 요구하지 않는다.
- 상대를 깎아내리거나 비꼬지 않는다. 부정적인 댓글에도 방어적으로 굴지 않는다.
- 거짓 긴급성을 만들지 않는다. 남은 수량과 가격 인상은 실제 규칙이므로
  물어보면 사실대로 말해도 된다.

<모르면>
모른다고 하는 게 지어내는 것보다 낫다.
"확인해서 알려드리겠다"도 좋은 답이다.
아는 척한 게 하나 걸리면 나머지 답도 다 의심받는다.

<톤>
- 한국어 존댓말. 3문장 이내, 최대 500자. 길면 안 읽는다.
- 이모지는 안 쓰거나 최대 1개. 느낌표 남발 금지.
- 광고 문구처럼 쓰지 않는다.

<행동 선택>
reply / skip / hide / escalate 중 하나를 고른다.
escalate 대상:
[목록 나열]
escalate 를 고르면 답글 본문은 비워 둔다.
```

### 출력을 구조화하십시오

모델이 자유 문장으로 답하면 **판단과 본문을 분리할 수 없습니다.**
아래 형식으로 강제하십시오.

```
{
  "action": "reply | skip | hide | escalate",
  "reply":  "action이 reply일 때 게시할 문장. 그 외에는 빈 문자열",
  "reason": "그 판단을 한 이유 한 문장 (기록용, 게시 안 됨)"
}
```

`reason` 을 남기는 게 중요합니다. 나중에 봇이 이상하게 굴 때 **어디서
판단이 틀렸는지** 이걸로 찾습니다.

### 발사 전 마지막 검사

모델이 형식을 지켜도 내용은 틀릴 수 있습니다. 코드에서 한 번 더 막으십시오.

- 본문이 비었으면 → skip 으로 강등
- 500자를 넘으면 → escalate 로 강등
- 모델이 응답을 거부했으면 → escalate
- JSON 파싱이 안 되면 → escalate

**의심스러우면 올리지 않는 쪽**이 항상 맞습니다.

## 8. 중계 봇 — 판매를 사건으로

예약 발행은 **시간이 오면** 나가고, 중계는 **사건이 생기면** 나갑니다.

### 사건 설계

| 사건 | 조건 |
|---|---|
| `launch` | 판매를 열었을 때 |
| `quiet-N` | 0건인 채로 N시간 경과 (예: 6, 12) |
| `first` | 첫 판매 |
| `count-N` | N건째 (예: 3의 배수) |
| `half` | 절반 |
| `almost` | 남은 수량이 소량 |
| `soldout` | 완판 |

**`quiet` 가 이 설계의 핵심입니다.** 안 팔리는 시간도 사건으로 잡으면
소재가 끊기지 않습니다.

### 도배 방지

수량을 몰아서 입력하면 사건이 한꺼번에 여러 개 걸립니다.
그대로 올리면 도배입니다.

**가장 중요한 사건 하나만 올리고 나머지는 지나간 것으로 표시**하십시오.
우선순위는 `soldout > almost > half > count > first > quiet > launch` 입니다.

### 수량은 사람이 입력합니다

플랫폼 정산과 자동 연동하지 마십시오. **숫자가 틀리면 중계 글이 거짓말을
하고, 그건 되돌릴 수 없습니다.** 그리고 **수량을 줄이는 건 막아두십시오.**
오타 한 번에 사건 기록이 꼬입니다.

### 중계 프롬프트

```
너는 스레드 계정 [계정명]의 글을 쓴다.
지금 하는 건 상품 홍보가 아니라 판매 과정 중계다.

<파는 것>
[상품명 / 한 줄 설명 / 가격 규칙]

<중계의 원칙>
- 한 편에 사건 하나만 다룬다. 지금 벌어진 일 하나.
- 상품 설명을 반복하지 않는다. 이미 아는 사람이 읽는다고 가정한다.
- 숫자는 주어진 사실만 쓴다. 없는 숫자를 만들지 않는다.
- 안 팔리면 안 팔린다고 쓴다. 그게 다음 화다.
- 마지막 줄은 다음이 궁금해지게 끝낸다. 억지 떡밥은 쓰지 않는다.

<절대 하지 않는 것>
- 수익 금액이나 성과를 약속하지 않는다.
- 주어진 사실에 없는 수치·후기·반응을 지어내지 않는다.
- 거짓 긴급성을 만들지 않는다. 남은 수량과 가격 인상은 실제 규칙이라
  그대로 써도 되지만, 없는 마감 시한은 만들지 않는다.
- 본문에 링크를 넣지 않는다. 링크는 사람이 첫 댓글에 단다.
- 자랑하는 톤을 쓰지 않는다.

<형식>
한국어. 500자 이내, 3~6줄 권장.
이모지는 안 쓰거나 최대 1개. 해시태그 금지.

지금 상황:
- 지금까지 팔린 수량: [n]
- 한정 수량: [total]
- 남은 수량: [left]
- 다음 구매자가 낼 가격: [price]
- 판매 시작 후 경과: [hours]시간

이번 글에서 다룰 것:
[사건별 각도 — 아래 참고]
```

**사건별로 각을 다르게 줘야 합니다.**

| 사건 | 각 |
|---|---|
| launch | 판매를 열었다는 사실. 실적이 없다는 걸 먼저 밝힌다. 파는 티는 최소로 |
| quiet | 몇 시간째 0건이라는 사실. 변명도 자조도 하지 않는다. 안 팔리는 이유를 스스로 추측해보는 것까지가 내용 |
| first | 첫 판매. 과장하지 않는다. 한 건은 한 건이다 |
| count | n건째와 가격 변동. 가격 규칙을 모르는 사람을 위해 한 줄로 다시 설명 |
| half | 절반. 남은 수량과 현재 가격 |
| almost | 몇 개 안 남았다는 사실. 실제 수량이므로 그대로 |
| soldout | 완판. 총 몇 개, 얼마에 시작해 얼마로 끝났는지. 감사와 다음 계획 |

### 최근 글을 함께 넘기십시오

같은 문장과 같은 구조가 반복되면 그 순간 봇으로 읽힙니다.
**직전 3~4편의 본문을 프롬프트에 함께 넣고 "반복하지 마라"**고 지시하십시오.

## 9. 전환을 만드는 배치

봇이 잘 돌아도 배치가 틀리면 안 팔립니다.

### 링크는 본문에 넣지 않습니다

본문에 외부 링크가 있으면 도달이 떨어집니다.
**본문에서는 "링크는 댓글에 두겠습니다"로 처리하고, 첫 댓글에 답니다.**

### 답변 글이 판매 글보다 많아야 합니다

최소 3:1. 이 비율이 무너지면 홍보 계정으로 분류되고 도달이 죽습니다.
아무도 안 물어보면 **자주 받는 질문을 스스로 던지고 답하십시오.** 그것도 됩니다.

### 가격은 정찰제로 두지 않습니다

오늘도 3만원, 내일도 3만원이면 오늘 살 이유가 없고 내일이면 잊습니다.

**한정 수량 + 건당 인상**을 겁니다. 효과가 세 겹입니다.

- **지금 살 이유**가 생긴다
- **중계 소재**가 생긴다 ("3건 나갔고 가격이 올랐습니다")
- **초기 구매자가 보상**받으므로 후기 요청이 자연스러워진다

**규칙은 공표하고 지키십시오.** 30개라 했으면 30개에서 닫습니다.
반응이 좋다고 늘리면 다음 판매에서 신뢰를 잃습니다.

### 현재 가격을 계속 노출합니다

인상이 보이지 않으면 정찰제와 같습니다.

## 10. 안전장치 — 계정을 죽이지 않기

자동화의 가장 큰 위험은 **하루 만에 계정이 정지되는 것**입니다.

### 한도는 API 한도보다 훨씬 낮게

API가 허용하는 건 글 250건/일이지만 **그건 상한이지 목표가 아닙니다.**
실제 상한은 알고리즘과 읽는 사람의 인내심입니다.

권장값은 **글 6건/일, 답글 80건/일** 정도입니다.
그리고 **24시간 이동 창으로 직접 세십시오.** 자정 기준으로 세면
밤 11시에 몰아 쓰고 새벽 1시에 또 쓰는 일이 생깁니다.

### 멱등성

같은 글을 두 번 올리거나 같은 댓글에 두 번 답하면 그 즉시 봇으로 읽힙니다.
**상태 파일에 기록하고, 실행할 때마다 먼저 확인**하십시오.

상태 파일을 쓸 때는 **임시 파일에 쓰고 이름을 바꾸는 방식**을 쓰십시오.
쓰는 도중에 프로세스가 죽으면 파일이 깨지고, 그러면 전부 다시 발행됩니다.

### 실패하면 멈춥니다

한 건이 실패했을 때 다음 건으로 넘어가면 **순서가 무너집니다.**
판매 글이 소개 글보다 먼저 나가는 사고가 여기서 납니다.
**멈추고 다음 주기에 다시 시도**하는 편이 낫습니다.

그리고 **4xx 오류는 재시도하지 마십시오.** 권한이나 토큰 문제라
다시 호출해도 같습니다. 5xx만 잠깐 기다렸다 재시도합니다.

### 금지 표현은 프롬프트와 코드 양쪽에서 막습니다

프롬프트에만 넣으면 언젠가 새어 나갑니다.
**발사 직전에 코드로 한 번 더 검사**하십시오.

- 수익 금액을 약속하는 표현
- 상품에 없는 기능
- 확인되지 않은 법·세무 단정
- 없는 마감 시한

### 사람에게 넘긴 건 따로 쌓으십시오

escalate 된 건을 로그에 섞어두면 놓칩니다.
**원문·작성자·링크·이유를 별도 파일에 쌓고** 하루 한 번 확인하십시오.

## 11. 그래서 무엇을 팔 것인가 — 페인포인트 지도

시스템이 준비됐으면 이제 태울 물건이 필요합니다.

**만들 것은 그 시스템이 매일 답하게 될 질문의 답**입니다.
답변으로 신뢰를 쌓고, 그 답의 완성판을 파는 구조입니다.

### 페인포인트를 찾는 방법

**하나. 검색해도 답이 없던 것.**
내가 직접 검색했다는 건 최소 한 명에게는 수요가 있었다는 증거입니다.
그리고 답이 없다는 건 시장에 자료가 없다는 뜻입니다.

**둘. 같은 걸 세 번 이상 설명한 것.**
이미 수요가 검증된 겁니다.

**셋. 상담 창구에 실제로 들어온 질문.**
시스템을 먼저 돌리면 **무엇을 만들지가 데이터로 나옵니다.**
이게 순서상 가장 좋습니다 — 만들고 나서 파는 게 아니라,
질문을 받고 나서 만듭니다.

### 카테고리별 페인포인트 예시

각 항목은 그 자체로 자료 하나의 주제가 됩니다.

**① 1인 판매자 · 소상공인**
- 주문·재고를 수기로 대조하는 데 드는 시간
- 반복되는 문의에 매번 같은 답을 쓰는 것
- 정산 내역을 엑셀로 맞추는 작업
- 상세페이지 문구를 매번 새로 쓰는 것

**② 사무직 · 실무자**
- 매주 같은 형식의 보고서를 다시 만드는 것
- 여러 파일에서 데이터를 모아 정리하는 것
- 회의록을 정리해 공유하는 것
- 메일·공문 초안을 매번 쓰는 것

**③ 콘텐츠 · 마케팅**
- 소재 발굴에 걸리는 시간
- 채널별로 같은 내용을 다시 쓰는 것
- 댓글 응대가 밀리는 것
- 성과 데이터를 모아 리포트로 만드는 것

**④ 프리랜서 · 대행**
- 견적을 얼마로 내야 할지 모르는 것
- 작업 범위가 계속 늘어나는 것
- 대금을 떼일까 걱정되는 것
- 레퍼런스가 없어 첫 건을 못 따는 것

**⑤ AI를 쓰지만 돈이 안 되는 사람**
- 무엇을 팔 수 있는지 모르는 것
- 만든 걸 어디서 파는지 모르는 것
- 결제·전달·법을 몰라 시작을 못 하는 것
- 사람이 없어 올려도 반응이 없는 것

### 자료로 만들 때

- **목록과 문장을 넣으십시오.** 원칙만 있으면 "그래서 뭘 하라는 건데"가 됩니다
- **그대로 복사해 쓸 수 있는 것**이 있어야 합니다. 프롬프트, 문안, 체크리스트
- **앞부분을 공개하십시오.** 미리보기가 후기 0개를 가장 잘 덮습니다
- **다루지 않는 것을 명시하십시오.** 신뢰가 여기서 나옵니다

## 12. 결제 · 전달 · 법무 최소 세트

시스템이 돌아도 결제가 없으면 매출이 0입니다. 최소한만 정리합니다.

### 채널 — 2026년 7월 확인 기준

| 플랫폼 | 수수료 | 자동 발송 | 사업자등록 |
|---|---|---|---|
| 래피드 | **1.6%** | 결제 즉시 | 불필요 |
| 리틀리 | **1~5%** | 결제 즉시 | 연 20건까지 불필요 |
| 크몽 | **4.4~16.4%** | 있음 | 필요 (심사) |
| 스마트스토어 | 결제 1.98~3.63% + 판매 2.73% | **없음** | 필요 |
| 토스페이먼츠 (PG) | 일반 3.4% / 영세 0.63% | 직접 구현 | 필요 (심사) |

**결제와 전달은 별개 문제입니다.** 결제 수단을 붙였다고 파일이 자동으로
가지 않습니다. 스마트스토어는 기본 기능에 자동 발송이 없어서 외부 도구가
필요합니다.

**채널 고르기 전에 이것만 물으십시오** — "결제가 끝나면 파일이 자동으로
갑니까, 제가 보내야 합니까?"

그리고 **본인이 직접 한 건 결제해 보십시오.** 다른 결제수단으로 사서
메일이 오는지, 파일이 열리는지 확인합니다. 5분이면 되고 사고를 막습니다.

### 법무 최소 세트

**통신판매업 신고**는 면제 기준이 있습니다.

> **직전 연도 통신판매 거래 50회 미만** **또는** **부가가치세법상 간이과세자**

"또는"입니다. 시작 단계라면 대부분 면제입니다.
다만 **면제라도 판매 페이지에 사업자 정보는 표시해야 합니다.**

**판매 페이지 필수 표기** — 상호 · 대표자명 · 주소 · 전화번호 · 이메일 ·
사업자등록번호 · 통신판매업 신고번호.
전화번호가 의무이므로 개인 휴대폰 대신 **통신사 투넘버**를 쓰십시오.

**환불 규정은 직접 쓰십시오.** "채널 정책을 따릅니다"로 끝내면 분쟁 시
불리합니다. 디지털 상품은 조건을 갖추면 청약철회를 제한할 수 있는데
**핵심 조건이 사전 고지**입니다.

```
[전달 전] 파일이나 링크를 보내드리기 전이면 전액 환불됩니다.
[전달 후] 청약철회가 제한됩니다. 디지털 파일은 전달 즉시 복제가 가능하기
          때문이며, 이 안내가 전자상거래법 제17조 제2항 제5호가 요구하는
          사전 고지입니다.
[하자]    열리지 않거나 설명과 다른 경우는 환불 대상입니다.
[미리보기] 구매 전에 앞부분을 확인하실 수 있습니다.
```

**수익 금액을 약속하지 마십시오.** 표시광고법 문제이고, 실무적으로도
그런 문구를 쓴 상품이 환불 요구가 가장 많습니다.

## 부록 A. 프롬프트 전문 {: .page-break }

> **공통 주의.** 모델은 모른다고 답하는 대신 **그럴듯하게 생성합니다.**
> 시장 규모, 경쟁사 목록, 법 조항 번호처럼 검증이 필요한 값을 요구하면
> 확신에 찬 오답이 돌아옵니다. 아래는 그런 값을 애초에 요구하지 않습니다.

### A-1. 응대 봇 시스템 프롬프트

7장 본문의 전문을 그대로 쓰십시오. 채울 자리는 다섯 개입니다 —
계정명, AI 이름, 운영자 경력, 상품 정보, escalate 목록.

### A-2. 중계 봇 시스템 프롬프트

8장 본문의 전문과 사건별 각 표를 함께 쓰십시오.

### A-3. 봇 코드 생성

```
스레드 공식 API로 도는 자동화를 만들려고 한다.
[Node.js / Python] 로 작성해라.

기능
1. 글 목록 파일을 읽어 아직 안 올린 글을 발행한다
2. 내 글에 달린 답글을 읽어 AI로 판단하고 답한다
3. 상태를 파일에 기록해 같은 작업을 두 번 하지 않는다

지켜야 할 것
- 발행은 두 단계다. 컨테이너 생성 후 잠깐 대기하고 발행한다
- 답글 조회는 내 글에 달린 답글을 가져오는 경로를 쓴다.
  내가 쓴 답글 목록을 쓰면 안 된다
- 응답에서 내가 쓴 답글은 걸러낸다
- 글자 수 500 제한. 이모지는 바이트로 계산되므로
  발행 전에 검사해서 초과하면 올리지 않는다
- 24시간 이동 창으로 발행 수와 답글 수를 직접 센다
- 상태 파일은 임시 파일에 쓰고 이름을 바꾸는 방식으로 저장한다
- 4xx 는 재시도하지 않는다. 5xx 만 잠깐 기다렸다 재시도한다
- 한 건이라도 실패하면 멈추고 다음 주기에 다시 시도한다
- 토큰은 환경변수에서 읽는다. 코드에 넣지 않는다

한글 주석을 달고, 단계별로 나눠서 제시해라.
내가 오류 메시지를 붙여넣으면 원인부터 짚고 수정본을 줘라.
```

### A-4. 발행 글 초안

```
계정 성격: [무엇을 다루는 계정인가]
운영자 상황: [실적 유무, 관련 경력]
파는 것: [상품과 가격 정책]

3일치 글을 써라. 하루 3편씩 9편.

배치
1일차 — 자기소개 / 문제 제기 / 내가 확인한 사실. 판매 언급 금지
2일차 — 실무 정보 무료 공개 / 상담 창구 여는 글. 판매 언급 금지
3일차 — 가격 정책 설명 / 오퍼

규칙
- 각 글 500자 이내
- 첫 글은 실적이 없다는 사실을 먼저 밝힌다
- 운영자 경력과 이 계정의 실적을 섞지 마라. 주어를 정확히 쓴다
- 수익을 약속하는 표현 금지
- 해시태그 금지, 이모지는 최대 1개
- 본문에 링크를 넣지 마라
- 각 글에 id 와 day 를 붙여라
```

### A-5. 상담 답변 초안 (수동용)

```
너는 [주제] 관련 질문에 답하는 담당자다.

원칙
- 판매와 무관한 질문에도 성실히 답한다
- 답변에 상품을 끼워 넣지 마라. 상대가 직접 물을 때만 안내한다
- 모르면 모른다고 하고 확인 후 답하겠다고 해라
- 금지: 수익·성과 약속 / 없는 기능 언급 / 법·세무 단정
- 판단이 서지 않으면 담당자 확인 필요로 표시해라

길이: 3문장 이내
```

### A-6. 페인포인트 발굴

```
내 상황: [경험한 일, 다뤄본 도구, 아는 업종]

이 조건에서 자료로 만들 수 있는 페인포인트 후보를 5개 뽑아라.

각 후보마다
1. 누가 겪는가 (구체적 상황으로. "직장인" 말고
   "주문·재고를 엑셀로 수기 관리하는 1인 쇼핑몰 운영자")
2. 지금 그 사람은 어떻게 때우고 있는가
3. 내가 직접 검증할 수 있는 검색어 3개
4. 자료로 만든다면 목차 5줄

금지
- 시장 규모나 수요를 숫자로 추정하지 마라. 네가 확인할 수 없다
- 실재하는 자료·서비스 제목을 예시로 들지 마라
- 수익 금액을 약속하는 표현 금지
```

### A-7. 자료 집필

```
주제: [정한 페인포인트]
독자: [구체적 상황]
분량: A4 기준 [ ]장

규칙
- 각 장은 독자가 실제로 막히는 지점 하나를 다룬다
- **수치·요율·법 조항·플랫폼 정책은 네가 쓰지 마라.**
  [확인: 무엇을 확인해야 하는지]로 표시하고 넘어가라. 내가 채운다
- 원칙만 쓰지 말고 목록과 문장을 넣어라.
  독자가 복사해서 바로 쓸 수 있어야 한다
- 마지막에 프롬프트와 체크리스트를 부록으로 넣어라

금지
- 수익 금액·기간·성공률을 약속하는 표현
- "누구나", "간단하게" 같은 난이도 축소 표현
- 저자의 실패담이나 신변잡기. 독자는 답을 사려고 지불했다
```

### A-8. 판매 페이지

```
아래 자료를 파는 페이지 문안을 써라.
[목차 붙여넣기]

구조
1. 후킹 — 독자가 지금 겪는 상태 한 문장. 상품 언급 금지
2. 문제 — 그 상태가 지속되는 이유
3. 다루는 것 (목차 기반)
4. **다루지 않는 것** — 반드시 넣어라
5. 미리보기 안내
6. 가격과 수량 정책
7. 환불 규정
8. 판매자 정보

금지
- 수익 보장 표현
- 없는 후기를 암시하는 표현
- 자료에 없는 내용을 약속하는 것.
  판매 페이지의 약속과 실제 내용이 다르면 그게 환불 사유다
```

### A-9. 출시 전 점검

```
아래를 출시 전 점검해라.
[문안 또는 프롬프트 붙여넣기]

점검 항목
1. 수익·성과를 약속하는 표현
2. 없는 후기를 암시하는 표현
3. 환불 규정에 전달 전/후/하자가 모두 있는가
4. 판매자 정보 7개 항목이 모두 있는가
5. 전달 방식과 소요 시간이 명시돼 있는가
6. 미기입 자리표시자
7. 검증되지 않은 사실을 단정한 문장
8. (봇 프롬프트라면) escalate 조건이 비어 있지 않은가

각 항목을 통과/실패로 판정하고 실패는 수정안을 제시해라.
```

## 부록 C. 확인 경로 {: .page-break }

본문 수치는 **2026년 7월 확인 기준**이며 변동됩니다.
API 사양과 플랫폼 정책은 특히 자주 바뀝니다.

| 항목 | 확인처 |
|---|---|
| 스레드 API 사양·한도 | 메타 개발자 문서 원문 |
| 필요한 스코프 | 앱 설정 화면의 권한 목록 |
| 토큰 유효기간·갱신 | 개발자 문서의 토큰 항목 |
| 플랫폼 수수료 | 각 서비스 요금 안내 |
| 내 스마트스토어 요율 | 정산관리 → 나의 수수료 정보 |
| 내 PG 수수료 등급 | PG사 관리자 → 가맹점 정보 |
| 통신판매업 면제 여부 | 관할 시청·구청 지역경제과 |
| 간이과세 여부 | 홈택스 → 사업자 정보 |
| 플랫폼 환불 규정 | 각 플랫폼 이용약관 **원문** |

### 확인 시 주의

**하나. 메타 문서는 도메인 표기가 섞여 있습니다.** 한쪽으로 통일해서
시험해 보고 되는 쪽을 쓰십시오.

**둘. VAT 포함/별도 표기가 없는 요율이 많습니다.** 기준을 통일하십시오.

**셋. "수수료"에 여러 종류가 섞여 있습니다.** 결제수수료와 판매수수료가
별개인 곳이 있습니다. 합산으로 비교하십시오.

### 출처

API 사양은 메타 개발자 문서, 플랫폼 요율은 각 서비스 공개 안내,
통신판매업 면제 기준은 공정거래위원회 고시, 법 조항은 전자상거래 등에서의
소비자보호에 관한 법률 원문 기준입니다.

오류를 발견하시면 알려주십시오. 개정판에 반영되며 같은 링크에서
최신본이 열립니다.
