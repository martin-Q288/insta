# 스레드 오토파일럿

공식 Threads API로 세 가지를 한다.

1. **판매 시작 전 글을 순서대로 발행한다** (`posts.md`)
2. **판매가 열리면 진행 상황을 중계한다** — 팔릴 때마다, 안 팔려도
3. **달린 답글에 답한다** — 판매와 무관한 질문까지

브라우저 자동화가 아니다. 로그인 세션을 조작하는 방식은 메타 약관 위반이고 계정
정지 위험을 지는데, 공식 API 한도가 **글 250건/일 · 답글 1,000건/일**로 필요량의
10~50배다. 위험한 쪽을 갈 이유가 없다.

## 중계가 예약 발행과 다른 점

예약은 **시간이 오면** 나가고, 중계는 **사건이 생기면** 나간다.

상품 소개는 한 번 하면 더 할 말이 없다. 그런데 판매 자체를 중계하면 쓸 거리가
계속 생긴다 — 첫 판매, 3권째, 가격 인상, 절반, 막바지, 완판. 그리고 결정적으로
**안 팔리는 것도 사건이다.** "6시간 지났는데 0건입니다"는 실패 보고가 아니라
다음 화 예고다.

`posts.md` 는 판매를 열기 전까지의 바닥이고, 그 뒤부터는 `bin/broadcast.mjs` 가
판매 상황을 보고 그때그때 쓴다.

## 이 계정은 상담 창구다

답글 봇은 판매 안내용이 아니다. **판매와 무관한 질문에도 답하고, 상품은 상대가
직접 물었을 때만 꺼낸다.** "자세한 건 전자책에" 같은 유도도 하지 않는다.

팔려고 쓴 글은 안 퍼지고 도와주려고 쓴 글은 퍼진다. 답이 좋으면 알아서 찾아온다.

## 무엇이 자동이고 무엇이 아닌가

| | |
|---|---|
| 자동 | 글 발행(일차 순서 강제), 판매 사건 중계, 답글 읽기·작성·게시, 욕설·스팸 숨기기 |
| 사람 | **판매 수량 입력**, 판매 링크를 첫 댓글에 다는 것, `config.escalate` 에 걸리는 답글 |

**판매 수량은 사람이 넣는다.** 플랫폼 정산과 붙이지 않은 건 의도적이다 —
숫자가 틀리면 중계 글이 거짓말을 하고, 그건 되돌릴 수 없다.

답글은 **초안 검토 없이 바로 게시된다.** escalate 항목만 예외로 빼두는 이유는
공개 답글이 잘못 나가는 비용이 늦게 답하는 비용보다 크기 때문이다. 전부 자동으로
돌리려면 `config.json` 의 `escalate` 를 `[]` 로 비우면 된다.

## 세팅 (30~60분, 한 번만)

### 1. 스레드 앱과 토큰

메타 개발자 콘솔에서 Threads 앱을 만들고 아래 권한으로 **장기 토큰**을 발급받는다.

| 권한 | 왜 필요한가 |
|---|---|
| `threads_basic` | 모든 호출의 기본 |
| `threads_content_publish` | 글·답글 발행 |
| `threads_manage_replies` | 답글 숨기기 |

- [앱 만들기](https://developers.facebook.com/documentation/threads/get-started/create-an-app)
- [토큰과 권한](https://developers.facebook.com/documentation/threads/get-started/get-access-tokens-and-permissions)
- [장기 토큰](https://developers.facebook.com/documentation/threads/get-started/long-lived-tokens)

장기 토큰도 만료된다. 72시간짜리 운영이면 문제없지만, 계속 돌릴 거면 갱신 주기를
확인해두세요.

### 2. 설정

```bash
cd threads
npm install
cp config.example.json config.json
```

`config.json` 에서 채워야 하는 것:

- `product.accountName`, `product.contact` — 나머지 `product` 항목은 이미 채워져 있고,
  **답글에 나갈 사실의 원천이다.** 여기 없는 기능·가격은 모델이 만들어내지 않는다.
  도구를 고치면 이쪽도 같이 고쳐야 한다.
- `escalate` — 사람이 봐야 하는 항목. 비우면 전부 자동.

**토큰은 환경변수로 넣는 걸 권한다** (설정 파일이 커밋되는 사고를 막는다):

```bash
export THREADS_USER_ID=...
export THREADS_ACCESS_TOKEN=...
export ANTHROPIC_API_KEY=...
```

`config.json` 과 `state/` 는 `.gitignore` 에 들어 있다.

### 3. 점검

아무것도 게시하지 않고 설정·토큰·키·글 길이를 전부 확인한다.

```bash
npm run check
```

여기를 통과한 다음에만 진행하세요.

## 실행

```bash
npm run publish -- --dry   # 무엇이 올라갈지만 출력
npm run publish            # 오늘 올릴 글 발행
npm run reply -- --dry     # 답글에 어떻게 대응할지만 출력 (게시 안 함)
npm run reply              # 답글 게시
npm run loop               # 10분마다 발행 + 중계 + 답글 반복 (무인 운영)
npm run loop -- --interval 300   # 5분 주기
```

`loop` 가 72시간 동안 돌아가는 프로세스다. `Ctrl+C` 한 번은 이번 주기를 마치고
정상 종료, 두 번은 즉시 종료.

### 판매 중계

```bash
npm run broadcast -- --launch        # 판매를 열었다고 표시 (이때부터 중계 시작)
npm run broadcast -- --sold 3        # 누적 3권으로 갱신하고 중계 한 편
npm run broadcast -- --sold 3 --dry  # 올리지 않고 무엇을 쓸지만 확인
npm run broadcast                    # 시간이 지나서 생긴 사건만 확인 (0건 경과 등)
```

**`--sold` 는 누적 수량이다.** 3권 더 팔렸으면 `--sold 3` 이 아니라 지금까지의
총합을 넣는다. 줄이는 건 막아뒀다 — 오타 한 번에 중계가 꼬인다.

한 번 실행에 **한 편만** 올린다. 0에서 갑자기 12권으로 갱신해도 사건 다섯 개가
한꺼번에 나가지 않고, 가장 중요한 하나만 쓰고 나머지는 접힌다.

사건 종류는 이렇다.

| 사건 | 언제 |
|---|---|
| `launch` | 판매를 열었을 때 |
| `quiet-N` | 0건인 채로 N시간 지났을 때 (기본 6, 12) |
| `first` | 첫 판매 |
| `count-N` | N권째 (기본 3의 배수) |
| `half` | 절반 |
| `almost` | 남은 수량 3권 이하 |
| `soldout` | 완판 |

**본문에 링크는 안 들어간다.** 링크는 사람이 첫 댓글에 단다. 본문에 외부 링크를
넣으면 도달이 떨어지는데, 그게 중계 전체의 효과를 깎는다.

가격·수량은 `config.json` 의 `sales` 에서 읽는다. **`book/latpeed.md` 의 숫자와
반드시 같아야 한다.** `npm run check` 가 판매 글과 대조해서 어긋나면 잡아준다.

**자동화의 실제 가치는 양이 아니라 반응 속도다.** 새벽 3시 댓글에 10분 안에 답이
가는 건 사람이 못 한다. 반대로 한도가 250건이라고 250개를 올리면 계정이 죽는다 —
기본값은 글 6건/일이고, 그게 상한이라고 보면 된다.

## 글 목록 — `posts.md`

```
# id: 01-result-hook
# day: 1
# 이 줄처럼 `#` 로 시작하는 줄은 주석 — 발행되지 않는다
본문 (최대 500자)
===
# id: 02-...
```

- `id` — 멱등성 키. 같은 id는 두 번 발행되지 않는다. 바꾸면 재발행된다.
- `day` — 첫 발행일로부터의 상대 일차. **판매 글이 1일차에 나가는 사고를 막는 장치다.**
  기본 9건은 1일차 3 / 2일차 3 / 3일차 3이고, 판매 글은 3일차에만 있다.
- `#` 로 시작하는 줄은 헤더 아니면 주석. 본문에서 빠진다.
- **`「」` 로 감싼 부분은 미기입 자리다.** 남아 있으면 `check` 가 실패하고
  `publish` 는 **그 지점에서 멈춘다** — 건너뛰면 뒤 글이 먼저 올라가서 순서가
  무너지는데, 그게 미기입 상태로 올라가는 것보다 나쁘다.
- 500자 제한. 이모지는 UTF-8 바이트로 계산된다(한글은 1자).

`loop` 는 매 주기 `posts.md` 를 다시 읽는다 — 돌아가는 중에 글을 추가할 수 있다.

### 순서가 이렇게 짜인 이유

| 일차 | 글 | 판매 |
|---|---|---|
| 1 | 자기소개 → 반응 속도 → 자동발송 확인한 것 | 없음 |
| 2 | 환불 규정 → 후기 0개 문제 → **상담 창구 열기** | 없음 |
| 3 | 가격 규칙 → 틀린 것 총정리 → 오퍼 | 여기서만 |

**자기소개가 첫 글이다.** 신규 계정이 결과물 자랑으로 시작하면 팔이 계정으로 읽힌다.

**상담 창구가 판매보다 먼저다.** 이게 순서의 핵심이다. 이틀 동안 답을 받아본
사람이 사흘째에 산다. 반대로 하면 아무것도 안 팔린다. 테스트가 이 순서를 강제한다.

오퍼 글이 나가고 판매를 열면, 그다음부터는 `posts.md` 가 아니라 중계가 이어받는다.

## 새 계정으로 시작하는 경우

- **첫 2~3개는 손으로 올려라.** 팔로워 0인 새 계정이 첫날부터 API로만 발행하는 건
  굳이 만들 필요 없는 스팸 신호다. 계정이 살아있는 걸 확인한 다음 `loop` 를 켜라.
- 프로필을 먼저 채워라. 빈 프로필 + 첫 글은 전환이 안 된다.
- 자기소개 글(`00-intro`)은 **없는 실적을 있는 척하지 않되, 있는 실적은 정확히
  밝힌다.** "AI로 뭘 팔아본 실적은 없습니다"로 시작하고, 그다음에 실제 판매
  경력(공동구매 중개, 통신판매업 신고 2021년, 운영 중인 스마트스토어)을 댄다.

  **이 구분이 핵심이다.** 그냥 "실적 없습니다"라고 하면 신뢰 구멍이 그대로
  남는다. 반대로 판매 경력을 AI 상품 실적인 것처럼 흐리면 과장이고, 하나가
  걸리면 나머지 주장도 같이 의심받는다. 앞의 것은 없고 뒤의 것은 있다 —
  그대로 말하는 게 가장 강하다.

  사업자등록·통신판매업 신고·운영 중인 스토어는 **열어보면 확인된다.** 후기와
  달리 조작이 안 되므로, 후기 0개를 덮는 가장 확실한 근거다.
  테스트가 이 구분을 강제한다.

### 어떤 계정을 쓸 것인가

기준은 하나다. **그 계정 팔로워 중에 이 상품을 살 사람이 있을 것 같은가.**

팔로워 300명짜리 관련 계정이 팔로워 0인 새 계정보다 압도적으로 낫다.
반대로 팔로워가 2,000명이어도 관심사가 다르면 새로 파는 게 맞다 — 기존
팔로워는 안 읽고, 새로 들어온 사람은 프로필을 보고 이탈한다. 도달만 깎인다.

관심사가 안 맞는 기존 계정이 있다면, **버리지 말고 한 번만 쓴다.**
새 계정을 소개하는 글을 기존 계정에 한 번 올리는 것이다. 전환율은 낮겠지만
0보다 낫고, 무엇보다 새 계정이 첫날부터 유령이 아니게 된다.
반복하지는 마라 — 관심 없는 사람에게 반복 노출하면 그 계정도 같이 죽는다.

## 상태 파일

| 파일 | 내용 |
|---|---|
| `state/state.json` | 발행한 글, 처리한 답글, 24시간 이동 창 카운터, **판매 수량과 중계한 사건** |
| `state/escalations.jsonl` | 사람이 봐야 하는 답글 (원문·작성자·링크·이유) |

`state.json` 을 지우면 **전부 다시 발행되고 중계도 처음부터 다시 나간다.**
백업하거나 건드리지 마세요.

## 하지 않는 것

- 여러 계정으로 자연스러운 호응을 꾸며내는 것 (바이럴 조작)
- 남의 글에 무관하게 답글을 다는 것 — 이 도구는 **내 글에 달린 답글**만 다룬다
- 수익·조회수 보장. 시스템 프롬프트가 이걸 금지하고 있고, 풀어야 할 이유가 없다
- **판매 수치를 지어내는 것.** 중계 글은 `state.json` 의 실제 수량만 쓴다.
  없는 숫자를 만들지 않도록 프롬프트에 사실 블록만 넘긴다
- 없는 마감 시한을 만드는 것. 남은 수량과 가격 인상은 실제 규칙이라 그대로 쓰지만,
  "오늘까지" 같은 건 만들지 않는다

## 테스트

```bash
npm test
```

목 HTTP 서버로 API 흐름을 검증한다 — 컨테이너 생성 → 발행 2단계, `reply_to_id`
전달, 4xx 재시도 안 함 / 5xx 재시도, 길이 계산, 상태 멱등성. 실제 자격증명 없이 돈다.

## 알려진 주의점

- **호스트 표기가 문서마다 다르다.** 메타 문서가 `graph.threads.com` 과
  `graph.threads.net` 을 섞어 쓴다. 기본값은 `.com` 이고 `config.threads.host` 로
  바꿀 수 있다.
- **모델은 `claude-opus-5` 기본값이다.** 답글 품질이 계정 신뢰도에 직결되므로
  기본을 낮추지 않았다. 비용을 줄이려면 `anthropic.model` 을 `claude-sonnet-5` 나
  `claude-haiku-4-5` 로 바꾸면 되는데, 그건 판단해서 선택하세요.
  거절 시 서버측 fallback 을 켜두었고, 지원되지 않는 환경이면 자동으로 일반 호출로
  내려간다.
